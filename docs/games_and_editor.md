> - **音效**在 G2 之后、G3 之前插入（最小音频，3~5 天）。
>
> 核心方法论：**游戏是引擎的验收测试，引擎版本由"能跑通哪个游戏"来定义。**

## 0. 方法论：游戏即验收测试

### 0.1 三条规则

1. **每个游戏都必须"只用引擎已有的能力"做完。** 当你想用某个能力而引擎没有时 → 那就是下一个引擎任务。**不要为了让游戏跑起来而在游戏代码里绕开引擎**（那会让引擎永远得不到该能力）。
2. **引擎版本号由游戏定义**：`v0.x.0` 的发布条件 = **某个游戏从"打开编辑器摆关卡"到"打包运行"全流程走通**。不是"功能写完了"，而是"游戏能玩了"。
3. **上一次的游戏必须永远能跑。** 每次引擎改动后，G1~Gn 全部回归。这就是 `upgrade_plan.md` §10 的"垂直切片"的扩展版——**多个切片，层层加码**。

### 0.2 为什么是"阶梯"而不是"一个游戏"

一个游戏无法覆盖所有引擎能力，而罗列"引擎应该有 200 个功能"无法排优先级。阶梯的用处：

| 作用 | 说明 |
|---|---|
| **排优先级** | 能力按"哪个游戏需要"排序。G2 需要的（编辑器/序列化/预制体）比 G4 需要的（UI 系统）更早做——因为游戏顺序由**玩法复杂度**决定，而玩法复杂度大致等于引擎复杂度 |
| **可交付** | 每个游戏都是一个**能给别人玩的东西**，而不是"引擎进度 60%" |
| **可回归** | 每个游戏都是永久测试用例；引擎改动后跑一遍全部游戏，就知道有没有破坏性变更 |
| **防镀金** | 游戏不需要的能力（3D、阴影、多后端）自然被推到"不需要做" |

### 0.3 反模式（明确不做）

- ❌ **为了引擎而做游戏**：如果某个游戏你根本不想玩，别做它——你会失去动力且验收标准会变成"能编译"。
- ❌ **先造完整引擎**：等你造完"完整引擎"，你已经忘了游戏要什么，而且时间线会失控 3 倍以上。
- ❌ **游戏代码里写引擎补丁**：游戏里出现的 `#ifdef` 或"临时绕过"，必须立刻转成引擎任务。
- ❌ **跳过 G1/G2 直接做想的那个游戏**：编辑器、序列化、预制体这些"无聊但必需"的能力必须在**小游戏**上验证过，否则会在主力游戏上以最难调试的形式爆炸。

## 1. 游戏阶梯总览

| # | 游戏 | 验收的引擎版本 | 一句话 | 引擎能力重点 | 估时 |
|---|---|---|---|---|---|
| **G1** | **Breakout**（已有雏形） | **v0.1.0** | 冒烟测试：证明渲染/输入/碰撞能跑 | 渲染批次、相机、输入、AABB 碰撞 | 3~5 天 |
| **G2** | **横版平台跳跃沙盒** | **v0.2.0** | **编辑器的诞生**：在编辑器里摆关卡并试玩 | 序列化、编辑器（视口/层级/检查器）、预制体、Play/Stop | 3~4 周 |
| **G3** | **幸存者类（Vampire Survivors 向）** | **v0.3.0** | **性能与脚本**：1,500 实体 60FPS + 全 C# 驱动 | 性能、脚本系统、RNG、对象池、空间分区 | 3~4 周 |
| **G4** | **开屏（开箱/抽卡）** | **v0.4.0** | **UI 编辑器 + UI 系统重构的验收场** | UI 系统（锚点/RectTransform）、多层弹窗、滚动列表、网格布局、文字、九宫格、数据表 | 3~4 周 |
| **G5** | **SLG 战棋**（`Into the Breach` / `Advance Wars` 向） | **v1.0.0** | **完整项目**：用前面所有能力做完并发布 | Tilemap、寻路、回合制、格子高亮、技能系统、战斗 UI、存档 | 8~12 周 |
| **G6** | **物理沙盒**（可选） | **v0.5.0** | 物理正确性与可复现性验证（可穿插在 G3/G4 之间） | 完整物理、确定性、调试绘制 | 1~2 周 |

**总计约 5~7 个月**（单人、每周 15~20 小时）。其中 G1+G2 是最关键的 6 周——**它会让你第一次拥有"能自己造关卡的游戏"**，之后就再也回不去了。

### 1.1 顺序理由（为什么这么排）

| 排序 | 理由 |
|---|---|
| G1 先 | 花 3~5 天把现有 Breakout 修成"真能玩"，同时验证渲染批次/相机/输入/碰撞的地基。**它是唯一一个已经有素材的游戏**，性价比最高 |
| G2 第二 | 编辑器是**所有后续游戏的杠杆**。有了"能摆关卡 + 试玩"，G3~G5 的关卡搭建时间从"改代码"变成"拖鼠标"。**这一投入必须在做主力游戏之前完成** |
| G3 第三 | 全 C# 驱动 + 高实体数。这一步把**脚本系统**和**性能**一次性压透。幸存者类是"最省的性能压力测试"：玩法极简、数量极大 |
| G4 第四 | UI 系统只能靠 UI 密集的游戏逼出来。卡牌游戏是"UI 为主、逻辑为辅"的最小完整形态 |
| G5 最后 | 主力游戏。**必须放在编辑器 + 脚本 + UI 都可用之后**，否则你会花 60% 时间在"缺少工具"上 |
| G6 可选 | 物理沙盒是**引擎质量**投资（确定性/可复现性），不是玩法需求。可随时穿插，也可以在 G5 需要精确物理时才做 |

### 1.2 横向能力：贯穿所有游戏

下面这些**不属于任何单个游戏**，但从 G2 开始就要持续投入（详见 `upgrade_plan.md` §9）：

- Debug HUD（FPS / DrawCall / 实体数 / 物理耗时）
- 控制台 + 命令（`scene.load`、`timescale`、`physics.debug`）
- 自动化截图（每次提交产出参照图，用于回归对比）
- 性能 CSV 记录（每局游戏结束后写一条，形成引擎性能时间线）

### G1 · Breakout —— 冒烟测试（引擎 v0.1.0）

**一句话**：把现有的 Breakout 从"能编译出画面"修成"真的能玩"。

**玩法**：挡板左右移动，反弹球，打掉 50 块砖，分数、生命、胜利/失败。

**明确不做**：不要加关卡、不要加道具、不要做菜单——**这个游戏唯一目的是冒烟测试**。

**引擎需求（必须已有）**

| 能力 | 说明 | 对应 `upgrade_plan.md` |
|---|---|---|
| 渲染批次正确 | 50 砖 + 球 + 挡板 + 文字，无 GL 错误 | A1~A5、A10、A11 |
| 相机可控 | 像素坐标与世界坐标一致，分辨率无关 | A9、F2 |
| 输入 | A/D 按住持续移动（`IsKeyDown`，不是 `IsKeyPressedOnce`） | S2.9 |
| AABB 碰撞 | 球 vs 砖/墙/挡板，含穿透修正（高速球不穿墙） | S4.1~S4.6 |
| 帧率控制 | `dt` 钳制，稳定 60FPS | S2.4 |

**C# 脚本要点**（这是脚本系统的第一个用例）

- `PaddleController`：读输入、限制在屏幕内。
- `BallController`：速度、墙面反弹、发球。
- `GameManager`：分数、生命、重开。
- **验收点**：这三段逻辑**全部用 C# 写**，C++ 里一行游戏逻辑都不许有。

**关卡与美术**：沿用现有 `BambooAssets/`（`arrow.png`/`armor.png`/`container.jpg`）+ 纯色矩形即可。

**验收标准**

| # | 判定 |
|---|---|
| 1 | 连续玩 5 分钟不崩、无 GL 错误（GL 调试回调计数 = 0） |
| 2 | 三种分辨率（800×600 / 1280×720 / 1920×1080）下玩法与视觉比例一致 |
| 3 | 球速提到 2000 px/s 时**不穿墙**（穿透修正生效） |
| 4 | 计分/生命/胜负判定正确；能重开 |
| 5 | 三段游戏逻辑都在 C# 里；改脚本数值 → 重载 → 生效 |
| 6 | 帧耗时稳定 < 4ms |

**暴露的引擎缺失**：文字渲染（分数必须显示）→ 若 A12 未做，本游戏会立刻暴露；音效缺失（可选）。

**产出**：`Sandbox/Games/G1_Breakout/` + README 里一段 GIF。

### G2 · 横版平台跳跃沙盒 —— 编辑器诞生（引擎 v0.2.0）

**一句话**：**在编辑器里摆出一个能玩的关卡并试玩**——这是整个计划的第一个"真正的里程碑"。

**玩法**：角色跑/跳/爬梯；20 个平台、10 个金币、尖刺、终点旗；相机平滑跟随；HUD 显示金币数与生命。

**明确不做**：不做敌人 AI、不做战斗、不做存档、不做多关卡流程（单关卡 + 编辑器足够）。

**引擎需求（这一版的**全部**新能力）**

| 能力 | 为什么这个游戏需要它 | 对应 |
|---|---|---|
| **场景序列化** | 关卡要存成文件 | `upgrade_plan.md` B1~B10 |
| **编辑器视口** | 要能看见并操作场景 | D5、D6、A8 |
| **Hierarchy / Inspector** | 要能选实体、改属性 | D7、D8 |
| **Play / Stop / Step** | 要能试玩并回到编辑态 | D12 |
| **预制体（Prefab）** | 平台和金币要能复制 20 份 | 新建（见下） |
| **父子层级 + 世界矩阵** | 角色带子节点（碰撞盒/精灵偏移） | S3.8 |
| **碰撞层 + 触发器** | 金币是触发器；尖刺与平台不同层 | S4.8 |
| **相机跟随** | 平滑跟随 + 边界限制 | A9 + 一个 `CameraFollow` 脚本 |
| **保存/加载快捷键** | Ctrl+S / Ctrl+O | D18 |
| **撤销/重做** | 摆关卡必须能 Ctrl+Z | D13 |

**新增引擎任务（`upgrade_plan.md` 里没有，由本游戏逼出）**

| # | 任务 | 说明 |
|---|---|---|
| P1 | **Prefab 系统** | `Prefab` 资源（一个实体子树的 JSON）+ 实例化（保持与源预制体的链接）+ "Apply / Revert"（编辑器里改实例后应用到预制体）。**这是编辑器能不能高效摆关卡的分水岭** |
| P2 | **编辑器网格吸附** | 摆平台时按格点吸附（可开关，默认 16px），否则拼出来的关卡会歪 |
| P3 | **多选 + 对齐工具** | 一次选 20 个砖块，左对齐/等距分布 |
| P4 | **场景视图导航** | 中键拖拽平移、滚轮缩放、F 聚焦选中、右键 WASD 飞行（2D 就是平移） |
| P5 | **可见性/锁定开关** | Hierarchy 里的小眼睛/小锁图标 |
| P6 | **碰撞体可视化** | 编辑器里画碰撞盒线框（依赖 A6 线绘制） |

**C# 脚本要点**

- `PlayerController`：跑（加速度 + 摩擦）、跳（土狼时间 coyote time + 跳跃缓冲 jump buffer——**这两个手感细节必须有**）、单向平台。
- `CameraFollow`：阻尼跟随 + 边界钳制。
- `CoinPickup`：`OnTriggerEnter` → 加分 → 销毁自身。
- `Hazard`：碰到 → 重生到检查点。

**关卡与美术**：用 `BambooAssets/Texture2d/` 现有素材 + 纯色块搭一个 30 秒可通关的关卡。**先只做一个关卡**——重点是把编辑器跑通。

**验收标准**

| # | 判定 |
|---|---|
| 1 | 从空场景开始，**只用鼠标**摆出完整关卡（不许手改 JSON） |
| 2 | 关卡存盘 → 关闭编辑器 → 重开 → 打开 → **完全一致**（截图对比） |
| 3 | 点 Play 试玩 60 秒 → 点 Stop → **场景与编辑前逐字段一致**（Play/Stop 无损） |
| 4 | 摆放过程中 Ctrl+Z 连续撤销 20 步 → 回到初始状态；Ctrl+Y 全部重做 → 回到最终状态 |
| 5 | 放一个预制体实例、改它的颜色、点 Apply → 场景里所有实例都变 |
| 6 | 相机在 0.5x / 2x 缩放下拖拽 100px，世界位移误差 < 1px |
| 7 | 5,000 实体的测试场景里编辑器 UI 帧耗时 < 8ms |
| 8 | 关卡里的平台/金币全部是**编辑器摆出来的**，零硬编码 |
| 9 | 全部游戏逻辑在 C# 里 |
| 10 | 打包后能独立运行，无编辑器依赖 |

**暴露的引擎缺失（预期会暴露）**：Prefab 的引用解析、实体层级序列化顺序、编辑器相机与游戏相机分离、Undo 的合并策略。

**产出**：`Sandbox/Games/G2_Platformer/` + `Assets/Scenes/*.bamboo.json` + GIF + **编辑器首次可用的录像**。

### G3 · 幸存者类 —— 性能与脚本（引擎 v0.3.0）

**一句话**：1,500 个实体的实时战斗，**全部逻辑用 C# 写**，稳定 60FPS。

**玩法**：玩家自动攻击，敌人从四周涌入，击杀掉经验，升级选 3 选 1 强化，存活 15 分钟。经典 Vampire Survivors 循环。

**明确不做**：不做多角色/多关卡/成就；不做联网。**只做一局**。

**引擎需求**

| 能力 | 为什么需要 | 对应 |
|---|---|---|
| **性能：大量实体** | 500~1500 敌人同屏 | A1~A4（批次）、P1/P2 |
| **脚本系统（真用起来）** | 每种敌人/武器/升级都是一个脚本 | E1~E19 |
| **空间分区** | 1,500 实体的碰撞不能 O(n²) | S4.4（SpatialHash） |
| **对象池** | 每帧生成/销毁几百个弹幕，不能每帧 new/delete | 新建（见下） |
| **确定性 RNG** | 升级选项要可复现（调试与平衡） | `Math/Random` 已有，需接入并做种子控制 |
| **脚本枚举所有实例** | "对所有敌人施加伤害"需要批量查询 | E3（组件注册表的查询）+ 批量迭代 API |
| **Debug HUD + 性能计时** | 要看清楚瓶颈在哪 | §9 |
| **对象池感知的销毁** | 敌人死亡回池，不是真销毁 | 池组件 |

**新增引擎任务**

| # | 任务 | 说明 |
|---|---|---|
| P7 | **对象池系统** | `PoolComponent` + `Spawner` API（`Spawn(prefab, pos)` / `Despawn(entity)`）；回池时重置组件；池容量监控（HUD 显示"池中/活跃"） |
| P8 | **批量查询 API（含脚本侧）** | 脚本需要"遍历所有带 X 组件的实体"：`hostApi->for_each(componentTypeName, callback)`。**不要**让脚本每帧为每个实体做一次跨语言调用——那会撞上 P7 的性能目标 |
| P9 | **帧时间预算与告警** | 超过 16.6ms 时记录"哪个系统超了"（配合 `BAMBOO_PROFILE_SCOPE`） |
| P10 | **确定性重放（可选但推荐）** | 记录输入序列 + 种子 → 重放同一局。**这是调平衡与抓 bug 的终极工具**，1,500 实体场景里价值极高 |

**C# 脚本要点**

- `EnemyController`（多种子类或用数据驱动：HP/速度/精灵由 `fields` 决定）
- `WeaponController`（自动索敌、冷却、弹幕生成）
- `ProjectileController`（飞行、命中、回池）
- `ExperienceController` + `LevelUpMenu`（UI 三选一——**这里会第一次真正用到 UI**，可能是 G4 的预演）
- `RunManager`（计时、难度曲线、结算）
- **性能要点**：脚本 `Update` 里**不许分配堆内存**（不用 LINQ、不用闭包捕获、用 struct）。这一条要写进脚本 API 文档并在 CI 里用分配检测兜底。

**关卡与美术**：一张无限平铺的地面 + 简单几何图形敌人（纯色圆/方块即可，**美术不是这个游戏的重点**）。

**验收标准**

| # | 判定 |
|---|---|
| 1 | 1,500 敌人同屏稳定 60FPS（帧耗时 < 16.6ms，1% low > 45FPS） |
| 2 | 物理步进 < 4ms；脚本 Update 总耗时 < 2ms |
| 3 | 一局 15 分钟不崩、无内存增长（对象池生效） |
| 4 | 连续 3 局之间无状态泄漏（重开一局全清） |
| 5 | 同一种子 + 同一输入序列 → 结果完全一致（若做了 P10） |
| 6 | 改一个敌人的数值脚本 → 热重载 → 立即生效，**不打断当前这一局**（脚本实例重建但游戏继续） |
| 7 | HUD 显示实体数/池占用/DrawCall，与实际相符 |
| 8 | 全部游戏逻辑在 C#；C++ 侧只提供 P7/P8 的引擎 API |

**暴露的引擎缺失**：批量迭代性能、脚本分配压力、UI 与游戏层的事件分发、对象池与序列化的交互（池中实体不该被存盘）。

**产出**：`Sandbox/Games/G3_Survivors/` + **一份性能报告**（`docs/perf/survivors-v0.3.0.csv`：实体数 × 帧耗时曲线）。

### G4 · 开屏（开箱/抽卡）—— UI 系统重构的验收场（引擎 v0.4.0）

> **已决策（2026-09-18）**：G4 = **开屏/开箱抽卡**。它同时承担两件事：(1) 逼出完整 UI 系统；(2) **作为 `Source/Bamboo/UI/` 重写为 ECS UI 的验收场**（决策依据见 §9.1）。

**一句话**：做出一个**能开箱、抽卡、收集、查看详情**的完整界面——整个游戏 90% 是 UI。

**为什么"开箱"是比卡牌更合适的 UI 验收场**：它把 UI 系统里最难的几件事**一次全压出来**，而逻辑极简（不需要战斗规则、不需要回合制、不需要平衡）：

| 开箱逼出的 UI 能力 | 为什么这是硬需求 |
|---|---|
| **多层弹窗 + 遮罩** | 主界面 → 开箱动画 → 结果弹窗 → 卡牌详情，**三层叠加**，必须正确处理遮罩与返回栈 |
| **滚动列表 / 网格** | 卡牌收藏可能上百张 → 需要滚动容器 + 网格排布 + 虚拟化（后期） |
| **同一预制体的 N 个实例** | 卡牌格 = 一个 UI 预制体实例化 100 次，**每张卡的图标/名字/稀有度颜色/数量都不同** → 这是"UI 预制体 + 数据绑定"的核心验证 |
| **稀有度与视觉分级** | 不同稀有度的边框/光效/底色 → 状态驱动的 UI 样式切换 |
| **进度条 / 资源数字** | 货币、保底进度、经验条 → 条状填充 + 数字滚动 |
| **布局在本分辨率下不跑版** | 卡牌网格最容易暴露锚点问题（列数固定、间距固定、容器居中） |
| **点击/悬停/长按/拖拽** | 悬停放大预览、长按看详情、拖拽排序收藏 |
| **状态切换与返回** | 界面栈（Push/Pop）、Esc 返回、动画过渡 |

**明确不做（防膨胀）**：

- ❌ 战斗系统（开箱游戏不需要战斗——那是 G5 的事）
- ❌ 卡牌养成/升级/合成（属于"内容深度"，不是 UI 验证）
- ❌ 联网/账号/抽卡概率合规（单机演示）
- ❌ 复杂动画系统（只做 tween：位移/缩放/透明度/数字滚动）
- ❌ 真实的付费/商店（用假货币即可）

**玩法范围（锁定）**

| 项 | 范围 |
|---|---|
| 界面数量 | **4 个**：主界面（货币 + 开箱按钮 + 收藏入口）、开箱动画页、结果页、收藏/详情页 |
| 卡池 | **30 张卡**（3 种稀有度），目录存 CSV/JSON |
| 一局时长 | 开一次箱 ≈ 10 秒；玩到你腻 ≈ 10 分钟 |
| 存档 | 单文件 JSON（货币 + 已获得卡牌列表）。**这是 G5 存档系统的预演** |

**引擎需求**

| 能力 | 为什么需要 | 对应 |
|---|---|---|
| **UI 系统（核心，重写）** | 整个游戏都是 UI | §9.1、P11~P16 |
| **RectTransform（锚点/轴心）** | 卡牌网格要居中、按钮要贴角 | P11 |
| **文字渲染（中英 + 数字）** | 卡名、描述、数值 | A12 |
| **九宫格（9-slice）** | 卡框/面板/按钮要能拉伸 | A13 |
| **UI 事件（点击/悬停/长按/拖拽）** | 全部交互 | P12 |
| **画布缩放策略** | 换分辨率不跑版 | P13 |
| **UI 层级与遮罩** | 三层弹窗 | P14 |
| **网格/垂直布局组件** | 卡牌网格、列表 | P15（**此处 GridLayout 必须做**，不能推迟） |
| **UI 预制体** | 卡牌格实例化 N 次 | §8.4（Prefab 已在 G2 做） |
| **数据绑定 / 数据表** | 30 张卡的数据来自文件，不是代码 | P17 |
| **Tween（简单补间）** | 开箱动画、数字滚动、悬停放大 | 新建 P18 |

**新增引擎任务**

| # | 任务 | 说明 |
|---|---|---|
| P11 | **RectTransform 组件** | `AnchorMin/AnchorMax/Pivot/AnchoredPosition/SizeDelta` —— 照抄 Unity 语义。**没有锚点就没有可用的 UI 布局** |
| P12 | **UI 事件系统** | 命中检测 + `OnClick/OnHover/OnPointerEnter/Exit/OnDrag/OnLongPress` + 事件冒泡 + `interactable`/`blocksRaycast`。**UI 事件与游戏世界输入必须分离** |
| P13 | **Canvas + 缩放策略** | `ConstantPixelSize` / `ScaleWithScreenSize`（参考分辨率 + 匹配模式）；**UI 与游戏世界分批渲染** |
| P14 | **UI 层级 / 遮罩 / 界面栈** | UI 内部排序层级；`Mask`/`RectMask2D`（滚动列表需要它裁掉溢出内容 → **这里必须做**）；`UIScreenStack`（Push/Pop + 返回键） |
| P15 | **UI 布局组件** | `HorizontalLayout` / `VerticalLayout` / **`GridLayout`**（列/行数、单元格尺寸、间距、内边距、对齐） |
| P16 | **UI 编辑器可视化编辑** | 见 §9：设计态边界框、锚点虚线、Rect Tool 拖拽改尺寸 |
| P17 | **数据表导入** | CSV/JSON → 结构化资源（卡池、稀有度、图标）。**让"加 10 张卡"不用改代码** |
| P18 | **Tween / 简易动画** | `Tween(position/scale/color/alpha/number, duration, easing)` + 一个 `TweenSystem`。**不要做关键帧动画编辑器**，够用即可 |
| P19 | **滚动列表** | `ScrollView`（内容 + 视口 + 滚动条 + 滚轮/拖拽滚动）+ `RectMask2D` 裁剪。收藏页上百张卡需要它 |

**C# 脚本要点**

- `GachaManager`：抽卡逻辑（权重、保底、伪随机种子可复现）、消耗/产出货币。
- `GachaScreen` / `RevealScreen` / `CollectionScreen`：**每个界面一个脚本**，负责界面生命周期（`OnEnable`/`OnDisable` → 刷新 UI）。
- `CardSlotView`：绑定一张卡的数据到 UI（图标/名字/稀有度边框/数量）→ **UI 预制体的标准用法**。
- `TweenHelper`：开箱动画、数字滚动。
- `SaveManager`：存/读单文件 JSON（货币 + 已获得卡牌）。
- **注意（警告）**：不要为每个界面写"手动查找控件"的代码（`FindChild("Button_1")` 那种）。正确做法是**在脚本字段上引用 UI 元素**（Inspector 里拖拽赋值），由序列化保存引用。**如果发现自己在按名字找控件，说明 UI 系统的引用机制缺东西。**

**关卡与美术**：**美术是重点**。卡面、稀有度边框、按钮、面板、图标、字体都要做到"看起来像成品"。这会把九宫格、字体、颜色、透明度、层级全部压出来。

**验收标准**

| # | 判定 |
|---|---|
| 1 | **整个游戏（4 个界面）全部在 UI 编辑器里搭出来，零硬编码坐标**；C# 里没有任何魔法数字坐标 |
| 2 | 在 1280×720 / 1920×1080 / 2560×1440 **以及竖屏 720×1280** 下布局都正确（锚点生效） |
| 3 | 卡牌格是**一个 UI 预制体实例化 N 次**，每张卡显示自己的数据（图标/名字/稀有度色/数量） |
| 4 | 三层弹窗（主界面 → 开箱 → 结果 → 详情）能正确遮罩、正确返回（Esc 逐层退出），不出现"下层被点到" |
| 5 | 收藏页 100+ 张卡滚动流畅（60FPS），内容被正确裁剪不溢出 |
| 6 | 抽卡 1,000 次不崩、不泄漏（对象池/回收正确）；相同种子 → 相同结果 |
| 7 | 卡池数据来自 CSV/JSON，改数据文件 → 热重载 → 界面立即更新（含新增一张卡） |
| 8 | 中英文混排正确显示，无乱码；数字滚动与进度条正确 |
| 9 | 关掉重开 → 货币与收藏**完全一致**（存档正确） |
| 10 | 鼠标在 UI 上时**不会**穿透点到游戏世界物体 |
| 11 | 全部逻辑与界面构建在编辑器 + C# 里完成；**未修改引擎源码** |
| 12 | **【重构验收】`Source/Bamboo/UI/` 已删除，UI 全部走 ECS 组件**（`CanvasComponent`/`RectTransformComponent`/`UIImageComponent`/`UITextComponent`/`UIButtonComponent`/`UI*LayoutComponent`），且 Hierarchy/Inspector/序列化/预制体对 UI 元素**无需特殊代码即可工作** |

**这一条（#12）是 G4 的真正目的**：如果为了让 UI 能在检查器里编辑、能存盘、能做预制体，你不得不在编辑器里为 UI 加"专用分支"，说明 UI 与 ECS 的整合没做对——**回去重做整合，而不是加分支**。

**暴露的引擎缺失（预期）**：UI 与 ECS 的整合方式、UI 渲染批次与游戏世界的分离、字体图集的生成工具、文本自动换行与对齐、UI 引用（脚本字段指向 UI 元素）的序列化。

**产出**：`Sandbox/Games/G4_Gacha/` + `Assets/UI/*.bamboo.json` + `Assets/Data/cards.csv` + **UI 编辑器可用录像** + 存档文件示例。

### G5 · SLG 战棋 —— 完整项目（引擎 v1.0.0）

> **已决策（2026-09-18）**：G5 = **SLG 战棋**（`Into the Breach` / `Advance Wars` / `火焰纹章` 这一路的走格子回合制）。参照类型：RPG。下面是为什么选 SLG 的分析。

#### G5.1 SLG vs RPG：作为"首个完整游戏"的对比

先明确一件事：**SLG 和 RPG 的引擎需求重叠度很高**，不是两个方向的选择题，而是"先做哪个"的顺序题。

| 引擎模块 | SLG 战棋 | RPG（剧情向） | 说明 |
|---|:--:|:--:|---|
| Tilemap（瓦片地图）渲染 | **●** | **●** | 两者都要 |
| 网格/格子系统 | **●** | ○ | SLG 的核心；RPG 只用于碰撞 |
| 寻路（A*） | **●** | ○ | SLG 必需；RPG 只有 NPC 游走（可省） |
| 回合制状态机 | **●** | ○ | SLG 是骨架；RPG 是实时/半实时 |
| 格子高亮 / 范围预览 | **●** | · | SLG 特有且**必须**（否则没法玩） |
| 单位选择 / 行动菜单 | **●** | · | SLG 特有 |
| 数据表（单位/技能/装备） | **●** | **●** | 两者都是数据驱动 |
| 战斗 UI（血条/伤害数字/行动条） | **●** | **●** | 两者都要 |
| 对话系统 | ○ | **●** | RPG 的核心体验之一 |
| 事件/触发器系统 | ○ | **●** | RPG 的"地图事件" |
| 背包 / 装备 / 商店 | ○ | **●** | RPG 必备 |
| 任务 / 日志系统 | · | **●** | RPG 必备 |
| 场景切换 / 大地图 | ○ | **●** | RPG 必备 |
| 存档（多槽位 + 世界状态） | **●** | **●** | 两者都要，RPG 更复杂 |
| AI | **●**（战术 AI） | ○（简单） | SLG 的 AI 是**核心难点** |
| 技能/效果系统 | **●** | **●** | 两者都要 |
| **需要的新子系统总数** | **约 6 个** | **约 11 个** | **这是决定性差距** |
| **内容量（剧本/美术/文本）** | 中（几张地图 + 10~20 单位） | **极高**（10~40 小时剧情 = 大量文本/美术/音乐） | 单人开发者的**头号杀手** |

#### G5.2 结论：选 SLG，理由按重要性排序

| # | 理由 |
|---|---|
| **1** | **新增子系统少一半**（约 6 vs 11）。RPG 要多做对话、事件、背包/装备/商店、任务日志、场景切换、大地图——**每一个都是独立模块**，而你只有一个人 |
| **2** | **内容量可控**。SLG 的"关卡"就是**一张地图 + 几个单位 + 一个胜利条件**——你可以只做 8~10 关就能发布，而且**关卡能在编辑器里摆**（G2 的预制体 + G4 的 UI 直接复用）。RPG 的内容量是它的 5~10 倍，且**内容不能用引擎能力替代** |
| **3** | **引擎需求与已有能力高度重叠**。SLG 需要的 tilemap + 格子 + 寻路 + 范围高亮，**是"渲染 + 物理形状 + UI"的自然延伸**，不需要新范式。RPG 需要的对话/事件系统是**另一套脚本运行时**，与现有 ECS 关系不大 |
| **4** | **可测试性极好**。战棋是**回合制 + 确定性**的：同样的操作序列必然得到同样的结果 → 可以写**自动化回放测试**（记录一局的输入序列，回归时重放比对）。这让你能对"完整游戏"做自动化验证——**RPG 的剧情流程几乎无法自动测试** |
| **5** | **AI 是可控的难点**。战术 AI 有明确边界（评估每个可行动作的收益），而且**做差了游戏也能玩**（随机选一个合法行动都比崩掉好）。相比之下，RPG 的"乐趣"高度依赖剧本与演出，**做差了就是无聊，且无法用工程手段救** |
| **6** | **素材门槛低**。战棋用**俯视图 + 纯色/简单像素块**就能做（`Into the Breach` 就是极简美术），美术可以边做边补。RPG 需要角色立绘、行走图、场景图、BGM——**美术量是发布不了的头号原因** |

**唯一让 RPG 更好的情形**：如果你**对某个 RPG 故事有强烈表达欲**，且接受"这是 1~2 年的项目"。那么热情能带你走完，工程理由都要让位。**但作为"第一台引擎上的第一个完整游戏"，SLG 是明显更优的工程决策。**

#### G5.3 SLG 范围锁定（防膨胀 —— 这一节最重要）

战棋最大的风险不是技术，是**范围**：很容易变成"我要做火焰纹章"。下面这张表**必须严格遵守**。

| 项 | **做** | **明确不做**（写进 README 的"不做清单"，防止自己反悔） |
|---|---|---|
| 地图 | 单张地图 **12×12 ~ 16×16** 格，固定关卡 | ❌ 大地图/世界地图 ❌ 程序生成 ❌ 地形高度/多层 |
| 单位 | **4~6 个单位**，**3 个兵种**（近战/远程/治疗） | ❌ 转职 ❌ 职业树 ❌ 装备槽 ❌ 等级成长系统 |
| 回合 | 玩家回合 → 敌方回合；**胜负条件 = 歼灭 / 占领 / 存活 N 回合** | ❌ 行动条/速度值 ❌ 同时回合 |
| 战斗 | 攻击 → 伤害计算（攻-防+浮动） → 反击（可选） | ❌ 命中/闪避/暴击的复杂公式 ❌ 战斗动画（只做位移 + 数字弹出） |
| 技能 | **6~8 个技能**，数据表驱动（范围/伤害/冷却/目标类型） | ❌ 技能树 ❌ 被动叠加 ❌ Buff/Debuff 的复杂结算（只做最简单的攻/防增减） |
| 地形 | **3 种**（平地/障碍/增益格，增益格 +20% 防御） | ❌ 多种地形组合 ❌ 地形改造 |
| AI | **3 条规则**：① 能打就打最近目标 ② 血少后退/治疗 ③ 否则向最近敌人移动 | ❌ 威胁评估/博弈/难度分级 ❌ 行为树编辑器 |
| 关卡数 | **8~10 关**（从教学到终局，难度递增） | ❌ 支线 ❌ 多结局 ❌ 剧情分支 |
| 剧情 | 每关一段**文字过场**（一张图 + 几行字，用 G4 的 UI 做） | ❌ 对话系统 ❌ 角色好感 ❌ 任务系统 |
| 存档 | **单档位**（关卡进度 + 单位状态） | ❌ 多槽位 ❌ 云存档 ❌ 自动存档的版本管理 |
| 美术 | 极简（纯色块/几何图形即可，参考 `Into the Breach`） | ❌ 角色立绘 ❌ 行走动画（用位移 tween 代替） ❌ 场景美术 |
| 音频 | **5~8 个音效**（移动/攻击/命中/治疗/UI 点击/胜利/失败 + 1 首 BGM） | ❌ 每关不同 BGM ❌ 音乐切换/淡入淡出（简单版即可） |

### G6 · 物理沙盒（可选）—— 物理与确定性（引擎 v0.5.0）

**一句话**：不做游戏，做**引擎质量验证**——物理对不对、稳不稳、可不可复现。

**内容**：一个可切换的场景集合（调试用，不是游戏）：

| 场景 | 验证什么 |
|---|---|
| 自由落体与抛体 | 与解析解对比（误差 < 1%） |
| 斜面滑动与摩擦 | 静摩擦/动摩擦、停止阈值 |
| 弹性碰撞（不同恢复系数） | 能量守恒/衰减 |
| 多球堆积（50~200 个球在箱子里） | **稳定性**：不抖动、不穿透、不发散 |
| 高速子弹穿墙测试 | 穿透修正 / CCD（连续碰撞检测） |
| 长链条/塔 | 迭代求解器的收敛性 |
| 确定性重放 | 同输入同种子 → 同结果（逐帧比对） |
| 性能压力 | 1,000 刚体步进耗时 |

**验收标准**

| # | 判定 |
|---|---|
| 1 | 抛体轨迹与解析解误差 < 1% |
| 2 | 200 个球在箱子里 60 秒后**全部静止**（不抖动、不发散） |
| 3 | 10,000 px/s 的子弹不穿墙 |
| 4 | 同输入 + 同种子重放，逐帧位置**完全一致**（bit-exact 或误差 < 1e-4） |
| 5 | 1,000 刚体步进 < 4ms |
| 6 | 调试绘制能显示碰撞体/接触点/速度矢量 |

**为什么值得做**：物理 bug 是**最难调试**的一类——它们往往只在特定数量/速度/顺序下出现。这个沙盒把"调物理"从"在游戏里碰运气"变成"跑固定用例"。**如果你要做塔防/弹幕/平台游戏里的任何精确物理，这项投资会在后面省下数倍时间。**

## 5. 编辑器设计总览（Unity 式）

### 5.1 设计目标（优先级从高到低）

| # | 目标 | 判定 |

| 3 | **能试玩** | Play/Pause/Step/Stop，Stop 后场景无损还原 |
| 4 | **能存读** | 场景与 UI 存成可读文件，能手工改 |
| 5 | **能管理资源** | 浏览、导入、拖拽到场景、看导入设置 |
| 6 | **不卡** | 5,000 实体场景下 UI 帧耗时 < 8ms |
| 7 | **可撤销** | 任何编辑操作都能 Ctrl+Z |

**明确不做（编辑器镀金清单，别碰）**：

- ❌ 多窗口 / 多显示器 / 独立窗口拖出
- ❌ 主题市场 / 自定义布局脚本
- ❌ 可视化脚本（节点图）——**C# 就是你的可视化脚本**
- ❌ 内置商店 / 版本管理 UI / 团队协作
- ❌ 动画曲线编辑器（除非 G5 明确需要）
- ❌ 材质/着色器图编辑器

### 6.6 使用流程：从零做一个游戏

这个流程本身就是编辑器的验收脚本：

1. `File ▸ New Scene` → 空场景（**不自动创建主相机**，由用户或用默认模板）
2. `GameObject ▸ Create Empty` → 叫 "Player"
3. Inspector ▸ `Add Component ▸ Sprite Renderer` → 拖一张贴图进来 → 设 Size
4. `Add Component ▸ Rigidbody2D` + `Box Collider 2D` → 调 Size 对齐精灵
5. Project 里右键 `Assets/Scripts` → `Create ▸ Script` → 命名 `PlayerController` → **自动生成脚本模板文件**
6. Inspector ▸ `Add Component ▸ Script` → 选 `PlayerController` → **自动列出 `fields` 并可编辑**
7. 把 Player 拖进 Hierarchy 成为平台子节点 / 或把平台拖成 Player 的兄弟
8. `File ▸ Save Scene`（Ctrl+S）
9. 工具栏 ▶ Play → 试玩 → ⏹ Stop（场景还原）
10. `File ▸ Build…` → 输出可运行目录

**这 10 步必须全部可用**——它就是 v0.2.0 的验收标准（见 G2）。

### 7.2 选择

| 操作 | 行为 |
|---|---|
| **左键点击** | 选中光标下最上层的实体（按渲染层级/Gizmo 优先） |
| **左键拖拽（空白处）** | 框选（矩形范围内全部选中） |
| **Ctrl + 点击** | 加选/减选 |
| **Ctrl + A** | 全选（可选：只选当前父级的子节点） |

**拾取实现**：鼠标 → `Camera::ScreenToWorld` → 与所有可见实体的世界 AABB/圆相交 → 按 `ZOrder` + 层级深度排序 → 取最上层。**复用物理的形状相交代码**（`upgrade_plan.md` S4.3），不要另写一套。

**性能**：实体多时（5,000）需要空间分区加速拾取，或在拾取时先用 AABB 粗筛。**拾取性能是编辑器不卡的隐性瓶颈**，G2 阶段就要留意。

### 7.3 Gizmo

| 模式 | 快捷键 | 交互 |
|---|---|---|
| **移动** | W | X/Y 轴箭头 + 中心自由拖拽；按住 Shift 拖拽限制在单轴 |
| **旋转** | E | 2D 场景用**一个圆环**（绕 Z 轴）；显示当前角度 |
| **缩放** | R | 轴端方块 + 中心统一缩放 |
| **Rect（UI 模式）** | T | UI 元素的锚点/轴心/边框拖拽（见 §9） |

**设计要点（决定了"手感"）**：

| 要点 | 说明 |
|---|---|
| **屏幕空间恒定大小** | Gizmo 不随相机缩放变大变小（按相机缩放反向补偿） |
| **拖拽平面求交** | 鼠标射线与"过物体中心、垂直于相机"的平面求交 → 得到世界位移。**2D 正交下这个计算很简单，但仍要写对**（用 `Camera::ScreenToWorld` 做增量即可） |
| **吸附** | Ctrl 临时吸附（或工具栏常开）；位置吸附 16px（可配）、旋转吸附 15° |
| **数值输入** | 拖拽时在 Gizmo 旁显示实时数值；Inspector 里可精确输入 |
| **一次 Undo** | 一次拖拽 = 一条 Undo 命令（拖动过程中合并） |
| **多物体 Gizmo 在重心** | 多选时 Gizmo 放在选中集合的中心 |
| **不遮挡** | 除 Gizmo 外，选中物体加**轮廓高亮**（用线绘制画 AABB 框即可） |

### 7.4 网格与辅助显示

| 元素 | 开关 | 说明 |
|---|---|---|
| 网格（Grid） | Gizmos ▸ Grid | 主格线 + 次格线，随缩放自动调整间距；**颜色要淡**（否则看不清物体） |
| 世界原点坐标轴 | Gizmos ▸ Axes | 红 X / 绿 Y |
| 碰撞体线框 | Gizmos ▸ Colliders | 绿色（静态）/ 黄色（触发器）/ 蓝色（动态） |
| 精灵边界框 | Gizmos ▸ Sprite Bounds | 淡蓝细框 |
| 相机视锥 | Gizmos ▸ Cameras | 相机可视野范围（2D 就是矩形） |
| 选中轮廓 | 自动 | 橙色 AABB 框 |
| UI 边界 / 锚点 | UI 模式自动 | 见 §9 |
| 物理接触点/速度 | Gizmos ▸ Physics Debug | 需要物理调试绘制（G6） |

### 7.5 鼠标状态与输入隔离

这是**最容易出 bug** 的地方，必须显式设计：

| 状态 | 判据 | 效果 |
|---|---|---|
| 鼠标在 Scene 视口内 | ImGui `IsWindowHovered()` | Scene 相机接受导航输入；游戏世界输入**屏蔽** |
| 鼠标在 ImGui 其他面板上 | 任一 ImGui 窗口 `WantCaptureMouse` | Scene **不**响应；游戏世界输入屏蔽 |
| 正在拖拽 Gizmo | 内部 `m_IsDragging` | 即使鼠标移出视口也**继续**拖拽（否则手感极差） |
| Play 模式 + 鼠标在 Game 视口 | Game 视口 `IsWindowHovered()` | **游戏世界输入开启**（这是唯一的游戏输入入口） |
| Play 模式 + 鼠标在编辑器面板 | `WantCaptureMouse` | 游戏世界**不**收到该次输入 |

**实现**：`EditorLayer` 在事件处理链的**最前面**，若 ImGui 想要输入就 `event.Handled = true`，游戏层收不到。`upgrade_plan.md` D1 的 Layer 事件路由就是这个用途。

## 8. 编辑器：摆物体工作流

这一节把"摆物体"拆成具体操作，**每一条都是 G2 的验收项**。

### 8.1 创建物体

| 方式 | 操作 | 说明 |
|---|---|---|
| 菜单 | `GameObject ▸ Create Empty` | 新空实体（带 Transform + Tag + ID） |
| 菜单 | `GameObject ▸ Create Child` | 创建为选中的子节点 |
| 快捷键 | `Ctrl+Shift+N` | 同上 |
| 拖拽资源 | 从 Project 拖贴图到 Scene | **自动创建**带 `SpriteRenderer`（贴图已设）的实体 |
| 拖拽预制体 | 从 Project 拖 `.prefab` 到 Scene | 实例化预制体 |
| 复制 | `Ctrl+D` | 复制选中并偏移一点（避免完全重叠） |
| 右键菜单 | Hierarchy 空白处右键 | Create Empty / UI 子菜单 / 2D Object |

### 8.2 变换

| 需求 | 实现 |
|---|---|
| 精确数值 | Inspector 里输入 Position/Rotation/Scale（拖拽数值标签可滑动改） |
| 鼠标拖拽 | Gizmo（§7.3） |
| 格点吸附 | 工具栏开关 + 数值；默认 **16px** 位置吸附 |
| 对齐工具 | 工具栏/菜单：左对齐/右对齐/水平居中/垂直居中/等距分布（多选时可用） |
| 复位 | Transform 组件右上角小齿轮 ▸ Reset Position / Reset Rotation / Reset Scale / Reset All |
| 世界 vs 本地 | 有父节点时，工具栏切换世界/本地坐标 |

### 8.3 层级（父子）

| 需求 | 实现 |
|---|---|
| 拖拽改父级 | Hierarchy 里拖到目标节点上 → **必须显示插入指示线**（放进去 vs 放在前后要能区分） |
| 保持世界位置 | 拖拽时按住 **Shift** = 保持世界位置（否则子节点会跟随父变换跳位）——**这是 Unity 的细节，直接抄** |
| 解除父级 | 拖到空白处，或 `Alt+Shift+G` |
| 展开/折叠 | 三角图标；`Alt+点击` 递归展开 |
| 可见性 / 锁定 | 每行的眼睛 / 锁图标；锁定的物体不能被 Scene 里点选 |

### 8.4 预制体（Prefab）

| 操作 | 说明 |
|---|---|
| 创建 | 把 Hierarchy 里的节点拖到 Project 面板 → 生成 `.prefab` 文件 |
| 实例化 | 从 Project 拖到 Scene，或 `GameObject ▸ Create From Prefab` |
| 编辑实例 | 改实例的字段 → Inspector 顶部显示 **Overrides（覆盖项）** 列表 + `Apply` / `Revert` 按钮 |
| 编辑源预制体 | 双击 `.prefab` 进入**预制体编辑模式**（独立场景）→ 保存后所有实例更新 |
| 嵌套预制体 | **先不做**（复杂度高，G2/G3 不需要） |

> **Prefab 是"摆物体"效率的核心。** 20 个平台不该是 20 份拷贝——如果 G2 里你发现自己"复制粘贴 + 手动改 20 次"，说明预制作得不够好。

| 操作 | 说明 |
|---|---|
| 框选 | Scene 里拖拽框选；Hierarchy 里 Shift/Ctrl 范围选择 |
| 批量改属性 | Inspector 显示共有组件的公共字段，改动应用到全部选中 |
| 批量删除/复制 | Delete / Ctrl+D |
| 对齐与分布 | §8.2 |
| 编组 | `Ctrl+G` 放到一个新空父节点下，**Gizmo 立刻变为组中心** |

### 8.6 撤销/重做覆盖范围

**必须支持 Undo 的操作**（G2 验收）：

| 操作 | 合并策略 |
|---|---|
| 改 Inspector 字段 | 连续拖同一个滑块合并为一条（松手提交） |
| Gizmo 拖拽 | 一次拖拽 = 一条 |
| 创建 / 删除 / 复制实体 | 各一条 |
| 拖拽改父级 | 一条 |
| 多选批量修改 | 一条 |
| 组件增删 | 一条 |
| 预制体 Apply / Revert | 一条 |
| 选择变更 | **不进 Undo 栈**（Unity 也不进） |
| 相机移动 | 不进 |
| Play/Stop | 不进（但 Play 状态本身要能还原） |

## 9. 编辑器：拼 UI 工作流

### 9.1 UI 的技术选型（**关键决策**）

现有 `Source/Bamboo/UI/` 是一个**独立的 retained-mode UI 框架**（`UIElement` + `UIComponent` + 自建子节点树 + `enable_shared_from_this`），**与 ECS 完全无关**，且大部分是空实现（见 `refactor_plan.md` P2-7）。

**我的建议：重写为基于 ECS 的 UI 系统。** 理由：

| 理由 | 说明 |
|---|---|
| **检查器自动可用** | UI 元素如果是实体，Inspector/Hierarchy/序列化/预制体**全部免费复用**。独立树意味着要给 UI 再造一套检查器、序列化、撤销 |
| **一套层级** | 不必维护"场景树 + UI 树"两套父子关系与两套遍历顺序 |
| **渲染统一** | UI 走同一个 `Renderer2D` 批次，只需要"UI 层在最上面"的排序规则 |
| **代价可接受** | `UIElement` 里真正有用的只有 `Position/Scale/Rotation/Size/Anchor` 和父子关系——这些在 ECS 里就是一个 `RectTransformComponent` |

**具体做法**：新增组件，删除 `UI/` 目录。

| 组件 | 字段 |
|---|---|
| `CanvasComponent` | `RenderMode`（ScreenSpaceOverlay 先做这一个）、`ReferenceResolution`、`ScaleMode`（ConstantPixelSize / ScaleWithScreenSize）、`MatchWidthOrHeight`、`SortOrder` |
| `RectTransformComponent` | `AnchorMin/AnchorMax`、`Pivot`、`AnchoredPosition`、`SizeDelta`（**取代 Transform**，UI 元素挂它而不是 `TransformComponent`） |
| `UIImageComponent` | `Sprite`/`AssetHandle`、`Color`、`ImageType`（Simple / Sliced / Tiled / Filled）、`FillAmount`、`PreserveAspect` |
| `UITextComponent` | `Text`、`Font`、`FontSize`、`Color`、`Alignment`、`HorizontalOverflow`/`VerticalOverflow`、`LineSpacing`、`RichText`（后做） |
| `UIButtonComponent` | `TargetGraphic`（指向哪个 UI 元素改色）、`NormalColor`/`HoverColor`/`PressedColor`/`DisabledColor`、`Transition`（Color / SpriteSwap / None）、`Interactable`、`OnClick`（脚本字段） |
| `UILayoutGroupComponent` | `Type`（Horizontal / Vertical）、`Padding`、`Spacing`、`ChildAlignment`、`ControlChildSize`、`ForceExpand` |
| `UIPanelComponent` | 纯容器（可选，用 UIImage 也能当容器） |

**`RectTransform` 的锚点语义（直接照 Unity 的定义，别自己发明）**：

```
父矩形：由父元素的 RectTransform 决定
AnchorMin/AnchorMax ∈ [0,1]²        锚点矩形（相对父矩形）
Pivot ∈ [0,1]²                       自身轴心
AnchoredPosition                     轴心相对"锚点矩形上的对应点"的像素偏移
SizeDelta 
  ├─ 当 AnchorMin == AnchorMax（点锚点）：SizeDelta = 实际尺寸
  └─ 当 AnchorMin != AnchorMax（拉伸）：SizeDelta = 相对锚点矩形的尺寸增量（负值=内缩）
```

> **务必照抄 Unity 的语义**。这是 UI 布局里最反直觉但也最标准的一套约定；自己发明一套会导致"换个分辨率就乱"而且没人能帮你调试。**写单元测试**：给定父矩形 + 锚点参数 → 期望的最终矩形（这部分是纯数学，**完全可测**）。

### 9.2 UI 编辑模式

在 Scene 视图里**切换模式**（工具栏一个按钮，或选中 Canvas 时自动进入）：

| 模式 | 显示 | 可交互 |
|---|---|---|
| **设计态（Design）** | UI 元素画**设计态边界**（`UIImage` 用半透明纯色块，即使没设贴图也能看见）；锚点虚线 + 角标；父子关系连线（可选） | 拖拽边框改 `SizeDelta`；拖拽锚点角改 `AnchorMin/Max`；拖拽轴心点改 `Pivot` |
| **运行态（Runtime）** | 显示真实渲染效果 | 只读预览 |

**设计态必须"即使没有贴图也能看见元素"**——否则你会面对一个空白视口不知道 UI 在哪。这是 Unity 的 `Rect Tool` + Gizmos 的做法。

### 9.3 UI 专属 Gizmo（Rect Tool，快捷键 T）

| 手柄 | 位置 | 行为 |
|---|---|---|
| **边框手柄**（4 边中点 + 4 角） | 元素边框上 | 拖拽改 `SizeDelta`（角 = 双向，边 = 单向） |
| **移动** | 元素内部拖拽 | 改 `AnchoredPosition` |
| **锚点手柄**（4 个小三角/菱形，在父矩形边缘） | 锚点位置 | 拖拽改 `AnchorMin`/`AnchorMax`；**Alt 拖拽 = 同时移动锚点与元素**（保持视觉位置） |
| **轴心点**（小圆圈） | 元素内 | 拖拽改 `Pivot` |
| **旋转** | 边框外一点 | 改 `Rotation`（UI 旋转较少用，可后做） |

**辅助显示**：

- 选中元素：**高亮边框** + 锚点虚线连到父矩形
- 父矩形轮廓：淡色虚线
- 数字提示：拖拽时显示 `AnchoredPosition` / `SizeDelta` 实时数值
- **分辨率下拉**：Scene 视图顶部一个下拉（如 `1920×1080`），切换后立即看到布局在不同分辨率下的表现——**这是锚点是否设对的最快验证手段**

### 9.4 拼 UI 的完整流程（G4 验收脚本）

1. `GameObject ▸ UI ▸ Canvas` → 自动创建 Canvas（含 `CanvasComponent` + `RectTransform`），若场景里没有相机则提示
2. `GameObject ▸ UI ▸ Image`（作为背景面板）→ 拖九宫格贴图 → 设 `ImageType = Sliced` → 锚点设为**全拉伸**（AnchorMin=(0,0), AnchorMax=(1,1), SizeDelta=(0,0)）
3. `GameObject ▸ UI ▸ Text` → 输入文本 → 选字体 → 设字号/颜色 → 锚点设为**左上角**（AnchorMin=AnchorMax=(0,1), Pivot=(0,1)）
4. `GameObject ▸ UI ▸ Button` → 设 Normal/Hover/Pressed 颜色 → 拖到合适位置
5. 在 Project 里给按钮挂一个 C# 脚本 `OnClickHandler` → 在 Inspector 里**把脚本的 `fields` 填上**（例如 `targetPanel`）
6. 切换分辨率下拉到 1280×720 / 2560×1440 / 竖屏 → **检查布局不跑版**（锚点正确的话应该都正常）
7. `Ctrl+S` 保存场景 → Play → 点按钮 → 面板显示/隐藏正确
8. Stop → 场景还原

**这 8 步必须全部可用**——它就是 v0.4.0 的验收标准。

### 9.5 UI 渲染顺序与遮罩

| 规则 | 说明 |
|---|---|
| UI 在游戏世界之上 | `Renderer2D` 分两批：世界批次 → 清深度/或直接后画；UI 批次 |
| UI 内部顺序 = 层级遍历顺序 | 父在前，子在后；同级按 `Hierarchy` 顺序（可拖拽调整，Unity 就是这样） |
| 弹窗遮罩 | 一个全屏半透明 `Image` + `blocksRaycast = true`（阻止下层交互） |
| 裁剪（Mask） | **先不做**；用"设计上避免溢出"绕开。真需要时再做 `RectMask2D` |

## 10. 编辑器与引擎的版本协同

用户要求"**编辑器、引擎和游戏互相迭代**"。这需要一个明确的协同机制，否则会变成"编辑器改坏了引擎"或"引擎改了编辑器崩"。

### 10.1 三条协同规则

| # | 规则 | 落地方式 |
|---|---|---|
| 1 | **编辑器用引擎的公开 API，绝不用内部实现** | 编辑器代码里出现 `#include` 引擎内部头（如 `Scene.cpp` 里的静态函数）就是违规。CI 用分层脚本检查 |
| 2 | **游戏需要的每个能力 → 先做进引擎 + 加测试，再在游戏里用** | 游戏代码里出现"绕过引擎"的 hack → 立刻转成引擎任务并记进 `docs/engine_backlog.md` |
| 3 | **每次引擎改动 → 跑全部已有游戏作为回归** | 这是"游戏即测试"的兑现。至少手动跑 G1~Gn 一遍 |

### 10.2 版本号规则

`vMAJOR.MINOR.PATCH`：

| 位 | 何时 +1 | 例子 |
|---|---|---|
| **MAJOR** | 存档格式不兼容，或引擎 API 大改（需要改游戏代码） | v1.0.0（发布）、v2.0.0（换渲染后端） |
| **MINOR** | 新增能力 / 某个游戏走通 | v0.2.0（G2 走通） |
| **PATCH** | 修 bug、调参数 | v0.2.1 |

**关键**：`MINOR` 与"游戏里程碑"绑定（§4）。**`v0.2.0` 这个号只发给"能在编辑器里摆关卡并试玩"那个提交**——这样版本号本身就是进度。

### 10.3 兼容性承诺（编辑器的生命线）

| 承诺 | 说明 |
|---|---|
| **场景/预制体/UI 文件向前兼容** | 新版本必须能打开旧版本文件（靠序列化版本迁移链，`upgrade_plan.md` B7）。**这条一旦破坏，你之前做的所有关卡都要重做** |
| **未知组件保留** | 用旧版本打开新场景，存盘后不能丢数据（B6） |
| **脚本 API 尽量稳定** | 改宿主 API 要加 `abi_version` 并在启动时明确报错，不要静默崩溃 |
| **.meta 与 GUID 稳定** | 改名/移动资源不破坏引用（C 模块） |

### 10.4 迭代循环（每个版本的实际节奏）

```
1. 选一个游戏（按 §1 的顺序）
2. 用它做 1~2 个玩法片段
3. 遇到"引擎没有的能力" → 记进 backlog
4. 按 backlog 优先级做引擎能力（附测试）
5. 回到游戏，继续做
6. 游戏这段做完了 → 跑全部旧游戏回归
7. 打 tag，写 CHANGELOG，录 GIF
8. 回到 1（下一个游戏，或同一个游戏的下一个系统）
```

**"backlog 驱动"而不是"清单驱动"**——这是游戏优先的核心。清单（`upgrade_plan.md` 的模块章节）是参考，实际做什么由**当前游戏卡在哪里**决定。

## 11. C# 脚本：兼容性纪律（AOT-clean）

既然定了 C# 路线，且将来可能要切 NativeAOT 发布（`upgrade_plan.md` §7.6 选项 D），那么**从第一天起就要守纪律**，否则将来切不过去。

### 11.1 硬性禁令（写进脚本 API 文档 + CI 检查）

| 禁止 | 原因 | 替代 |
|---|---|---|
| `System.Reflection`（除宿主类发现） | NativeAOT 下受限/不可用 | 显式注册脚本类 |
| `Type.GetType(string)` | AOT 下不可靠 | 类名 → 类型的静态映射表（用 source generator 或手写注册） |
| `dynamic` / `Reflection.Emit` / `Expression.Compile` | AOT 完全不支持（`Linq.Expressions` 在 AOT 下永远解释模式） | 用 `delegate` / 手写分支 |
| `Assembly.LoadFile` / 动态程序集 | AOT 不支持 | 静态引用 |
| 泛型虚方法派发（**特别提醒**） | .NET 10 上反复 load/unload 后有挂死回归（[#132562](https://github.com/dotnet/runtime/issues/132562)） | 避免在脚本基类上用泛型虚方法 |
| 脚本 `Update` 里的堆分配（`new` 对象、LINQ、闭包捕获、装箱） | GC 尖峰 + 帧时间抖动（G3 要靠这个达标） | `struct`、池化、预分配数组、`for` 循环 |
| 在脚本里长期缓存组件指针 | ALC 重载后悬垂（`upgrade_plan.md` §7.4） | 每帧通过句柄重新取 |
| 跨边界传 `string`/`bool`/数组作为导出参数 | 非 blittable，导出侧不接受 | `byte*` + `len`；`bool` → `byte` |

### 11.2 必做的三件事

| # | 事项 | 说明 |
|---|---|---|
| 1 | **结构体布局自检** | 启动时 C# 上报 `Marshal.SizeOf<T>()`，C++ 上报 `sizeof(T)`（含每个字段偏移），不一致就**明确报错**。C++ 侧再加 `static_assert` 锁死 |
| 2 | **脚本类显式注册** | 不用反射扫描，脚本工程导出一个类名表（或 `[BambooScript]` + source generator 生成注册代码）。这样 AOT 下可用，也能给编辑器的下拉列表用 |
| 3 | **分配检测（可选但推荐）** | Debug 下用 `GC.GetAllocatedBytesForCurrentThread()` 前后差值检测脚本 `Update` 的分配，超阈值就告警。G3 的性能目标靠它守 |

### 11.3 脚本工程的构建方式

| 阶段 | 方式 |
|---|---|
| 早期（G1~G2） | `dotnet build` 脚本工程 → 输出 `BambooScripts.dll` → 编辑器启动时加载（CoreCLR + 可卸载 ALC）；**编辑器里按一个按钮重编译 + 重载** |
| 中期（G3~G4） | 同上 + 文件监听自动重编译（配合资源热重载） |
| 发布（G5） | 同一份脚本源码，用 `-p:PublishAot=true -p:NativeLib=Shared` 出原生库，`LoadLibrary` 加载（**注意：发布态没有热重载**，这没问题，玩家也不需要） |

**关键**：目标框架先定 `net9.0`（本机只有 9.0.305 SDK / 9.0.9 运行时，**可以立刻开工**），正式发布前升级到 **`net10.0`（当前 LTS）** 并把 `TargetFramework` 一起改掉。**现在就装 .NET 10 SDK 更好**，免得后面迁移。
